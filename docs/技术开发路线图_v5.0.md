```sql
-- 商品搜索索引
CREATE INDEX idx_products_search ON products(category_id, status, created_at DESC);
CREATE INDEX idx_products_location ON products(province, city, status);
CREATE INDEX idx_products_price ON products(price, status);
CREATE INDEX idx_products_seller ON products(seller_id, status, created_at DESC);

-- 聊天索引
CREATE INDEX idx_chat_messages_room_time ON chat_messages(chat_room_id, sent_at DESC);
CREATE INDEX idx_chat_rooms_user_time ON chat_rooms(buyer_id, seller_id, updated_at DESC);
CREATE INDEX idx_chat_messages_unread ON chat_messages(chat_room_id, is_read, sent_at DESC);

-- 交易索引
CREATE INDEX idx_transactions_buyer ON transactions(buyer_id, status, requested_at DESC);
CREATE INDEX idx_transactions_seller ON transactions(seller_id, status, requested_at DESC);
CREATE INDEX idx_transactions_product ON transactions(product_id, status);

-- 用户相关索引
CREATE INDEX idx_favorites_user_time ON product_favorites(user_id, created_at DESC);
CREATE INDEX idx_notifications_user_read ON user_notifications(user_id, is_read, created_at DESC);
```

### Week 5-7: Elasticsearch搜索引擎集成 ⭐⭐⭐⭐⭐

#### 为什么需要Elasticsearch?

```yaml
MySQL全文搜索的局限:
```


```yaml

  ✅ 故障隔离: 单个服务故障不影响其他服务
```

### Week 19-22: 分库分表方案 ⭐⭐⭐

#### 为什么需要分库分表?

```yaml
单库单表的瓶颈:
  ❌ 数据量大: 单表超过1000万性能急剧下降
  ❌ 并发低: 单库连接数有限 (MySQL默认151)
  ❌ 磁盘IO: 单机磁盘IO成为瓶颈
  ❌ 备份慢: 数据量大备份恢复时间长

分库分表优势:
  ✅ 数据分散: 单表数据量控制在合理范围
  ✅ 并发提升: 多个数据库实例分担压力
  ✅ IO分散: 分散磁盘IO压力
  ✅ 易于扩展: 可动态增加分片
```

#### 分片策略

```yaml
垂直拆分 (按业务):
  原来: fliliy_db (所有表)
  拆分后:
    - user_db      (用户、地址、通知)
    - product_db   (商品、分类、收藏)
    - chat_db      (聊天室、聊天消息)
    - transaction_db (交易记录)

水平拆分 (按数据量):
  1. 用户表分片 (按用户ID取模)
     users_0, users_1, users_2, users_3
     规则: user_id % 4

  2. 商品表分片 (按商品ID取模)
     products_0, products_1, ... products_15
     规则: product_id % 16

  3. 聊天消息分片 (按时间分片)
     chat_messages_202501, chat_messages_202502, ...
     规则: 按月份分表，保留最近12个月

  4. 交易记录分片 (按时间+用户ID)
     transactions_0_202501, transactions_1_202501, ...
     规则: (user_id % 4) + 月份
```

#### 技术选型

```yaml
推荐方案: ShardingSphere
  ✅ 功能强大: 支持分库分表、读写分离、分布式事务
  ✅ 易于集成: JDBC驱动替换即可
  ✅ 性能好: 基于客户端分片，无额外跳转
  ✅ 生态完善: Apache顶级项目

ShardingSphere组件:
  - ShardingSphere-JDBC: 客户端分片 (推荐)
  - ShardingSphere-Proxy: 代理端分片
  - ShardingSphere-Sidecar: 服务网格 (未来)
```

### Week 23-24: Kubernetes容器编排 ⭐⭐

#### 什么是Kubernetes?

```yaml
Docker Compose的局限:
  ❌ 单机部署: 无法跨多台服务器
  ❌ 手动扩展: 需要手动增加容器
  ❌ 无自愈: 容器挂了需要手动重启
  ❌ 无滚动更新: 更新时服务中断

Kubernetes优势:
  ✅ 自动扩缩容: 根据负载自动增减Pod
  ✅ 自我修复: 容器挂了自动重启
  ✅ 服务发现: 内置服务发现和负载均衡
  ✅ 滚动更新: 零停机更新
  ✅ 配置管理: ConfigMap和Secret
  ✅ 资源调度: 智能调度到合适节点
```

#### 核心概念

```yaml
K8s核心概念:
  Pod: 最小部署单元，包含一个或多个容器
  Deployment: 管理Pod副本，支持滚动更新
  Service: 服务发现和负载均衡
  Ingress: HTTP/HTTPS路由规则
  ConfigMap: 配置管理
  Secret: 敏感信息管理
  PersistentVolume: 持久化存储
  Namespace: 资源隔离
```
